# 批处理取消与清单追溯修复设计

**背景**

本轮复审发现当前改动虽然已经解决了 GPU 修复参数语义冲突和批处理追溯基础字段缺失的问题，但仍残留 3 个会影响稳定性或追溯准确性的风险：

1. 批处理线程在特定取消时机会返回错误类型，导致取消结果可能被上层误记为失败。
2. `SignalHandler` 会缓存上一轮批处理的 `ai_params`，但在清空/替换队列时没有失效，可能让新队列导出的 manifest 混入旧任务参数。
3. 批处理运行配置只从活动中的 `batch_processor` 读取，任务结束后导出 manifest 时会丢失真实运行时的并发与重试配置。

**目标**

本次修复要做到：

- 取消路径始终返回统一的 `(status, error_message, processing_details)` 三元结构。
- manifest 在“任务完成后导出”和“队列重建后导出”两类场景下都能给出正确、可解释的运行参数来源。
- 补齐回归测试，锁定上述 3 个边界。

**方案选择**

方案 A：最小化修复现有链路。

- 在 `BatchProcessorThread` 内修正取消分支返回值。
- 在 `SignalHandler` 中引入“最近一次批处理运行快照”，与当前活动线程解耦。
- 在队列清空/重建时主动清空旧快照，避免跨批次污染。

优点：

- 影响面小，主要改动集中在当前已经修改过的热点文件。
- 能直接复用现有 manifest 结构，不引入新的导出协议。
- 回归测试容易补齐。

缺点：

- manifest 仍然基于“最近一次运行快照”语义，不是完整的运行历史。

方案 B：引入独立的批处理运行记录对象。

- 将 `ai_params`、并发配置、时间戳统一封装为独立状态对象。
- 导出 manifest 时仅从该对象读取。

优点：

- 语义最清晰，后续可扩展为多次运行历史。

缺点：

- 改动面更大，当前需求没有必要。

**推荐**

采用方案 A。它能以最小改动修复当前明确缺陷，并为后续如需扩展 `schema_version` 或历史运行记录保留空间。

**测试策略**

- 为 `BatchProcessorThread` 增加“取消分支返回三元组”的单元测试。
- 为 `SignalHandler` 增加 manifest 导出回归测试：
  - 任务完成后应保留最近一次运行的 `ai_params` 与批处理配置。
  - 清空队列或重新导入新队列后，不应继续复用旧运行参数。
