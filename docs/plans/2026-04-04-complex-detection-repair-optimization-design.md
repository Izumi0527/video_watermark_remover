# 复杂检测与修复优化设计

## 1. 目标

在不破坏当前默认稳定性的前提下，提升本项目在以下场景下的效果上限：

- 复杂图片：半透明水印、斜边 Logo、镂空文字、强纹理背景、反光背景、压缩噪声背景
- 复杂视频：移动/缩放/透视变化水印、运动模糊、强压缩、长视频、4K 素材

本轮设计不追求一次性“换一整套新模型”，而是先把现有架构中已经具备雏形的能力组织起来，再为更强的视频级方案留出清晰扩展位。

---

## 2. 当前现状

### 2.1 当前主链路

项目当前主链路已经比较清晰：

1. UI 收集高级参数并在 `AIParamsBuilder` 中收敛为统一 `ai_params`
2. `SignalHandler` / `BatchProcessorThread` 启动 `VideoProcessorThread`
3. `VideoProcessorThread` 根据运行时护栏选择 `single_process / pipeline / multiprocess`
4. `AIHandler` 统一协调检测、掩码处理、修复后端路由、回退和 trace
5. 视频模式层负责帧读取、处理、写回、音频保留和输出策略

### 2.2 已经落地的能力

本项目并不是“只有基础 YOLO + OpenCV”：

- `YOLOWatermarkDetector` 已支持单帧检测、批量检测、分割结果优先转掩码、bbox 到掩码的后处理
- `AIHandler` 已支持批量检测、批量 LaMa 修复、掩码收缩、掩码复用跟踪、混合修复策略
- `LaMaInpaintingBackend` 已支持 ROI 裁剪、运行时 resize limit、批量分桶、OOM 退避
- `OpenCVInpaintingBackend` 已经具备幂等加载
- 视频运行模式已有安全护栏，能避免 GPU 深度修复在高风险并行路径下崩溃

这些基础设施意味着：本项目更适合“增量增强 + 分层抽象”，而不是推倒重来。

---

## 3. 本轮审查确认的问题

### 3.1 正确性问题

- 多进程分块合并存在顺序错误风险：当前按路径字符串排序 `chunk_paths.sort()`，当块编号超过 9 时可能拼接错序

### 3.2 工程契约问题

- `AIParamsBuilder` 对 GPU 修复可用性的判断依赖 `torch` 是否已预加载到 `sys.modules`
- 批处理包装器内部方法签名已经演进，但对应测试桩未同步，导致门禁失真

### 3.3 复杂图片的上限瓶颈

- 当前复杂图片的核心瓶颈仍是掩码质量，而不是修复算法本身
- 在没有高质量掩码的前提下，任何修复后端都会出现残留、边界发虚或过修
- 当前主路径仍常回落到矩形掩码思维，对斜边、透明边、镂空结构的拟合能力有限

### 3.4 复杂视频的上限瓶颈

- 当前“跟踪”本质上更接近上一帧掩码复用，不是真正的视频时序传播
- 深度修复为了稳定性被运行时护栏限制在串行路径，吞吐上限受限
- 流水线和多进程解决的是并发问题，不等于解决时序一致性问题
- 当前修复后端仍以图像模型为主，复杂动态视频容易出现闪烁和边界漂移

## 4. 方案比较

### 方案 A：在现有主链上做增量增强

核心思路：

- 保留当前 `YOLO + OpenCV / LaMa` 主架构
- 引入独立的 `MaskRefiner`
- 引入独立的 `TemporalCoordinator`
- 在视频侧增加“关键帧检测 + 中间帧传播 + 失配重检 + 区域级去闪烁”

优点：

- 与现有代码最兼容
- 可以复用现有批量检测、LaMa ROI、运行时 profile、trace 体系
- 风险最低，适合作为主线方案

缺点：

- 视频质量上限仍受单帧修复模型限制
- 对极复杂动态水印的提升有限

### 方案 B：检测与时序解耦

核心思路：

- 检测仍用 Ultralytics
- 掩码传播与时序跟踪改由视频分割/跟踪组件承担
- 当前修复层保持不变

优点：

- 能显著提升复杂视频下的掩码稳定性
- 能减少“重复检测”和“掩码跳动”

缺点：

- 需要引入更复杂的状态管理
- 显存与推理时延会增加

### 方案 C：引入视频级高质量修复后端

核心思路：

- 默认模式继续使用当前 OpenCV / LaMa
- 新增“实验性高质量视频修复模式”
- 仅在复杂视频场景启用视频级时序修复模型

优点：

- 复杂视频上限最高
- 最适合长视频、复杂动态水印、连续纹理背景

缺点：

- 接入成本高
- 评测、显存、推理成本都明显更高
- 不适合作为当前默认主路径

### 推荐

推荐采用：

1. 主线采用方案 A
2. 方案 B 作为中期增强
3. 方案 C 作为实验性高质量模式

原因：

- 现有代码已经具备很多方案 A 所需积木
- 方案 A 能最快把“复杂图片/复杂视频”的主痛点打掉
- 方案 B/C 应该建立在更清晰的抽象和更稳定的评测基线上，而不是直接硬接入

## 5. 推荐架构

### 5.1 目标分层

建议把当前“很多策略集中在 `AIHandler`”的状态逐步拆成以下职责：

- `Detector`
  - 负责单帧/批量检测
  - 输出原始 boxes / masks / scores
- `MaskRefiner`
  - 负责把原始检测结果转换成更适合修复的 mask
  - 统一处理 padding、膨胀/腐蚀、边缘收缩、透明边修整
- `TemporalCoordinator`
  - 负责关键帧检测、掩码传播、失配重检、时序平滑
- `InpainterRouter`
  - 负责按场景把掩码分发到 OpenCV / LaMa / 实验性视频后端
- `QualityObserver`
  - 负责采集残留、闪烁、回退、显存与性能指标

### 5.2 为什么这样拆

- 当前 `AIHandler` 既做检测又做修复又做时序又做 trace，继续堆功能会让维护成本急剧上升
- 复杂视频优化必须让“检测、跟踪、修复、观测”成为可组合策略，否则每次增强都会在一个大类里继续膨胀
- 未来若接入 `SAM 2`、`ProPainter`、`E2FGVI` 或其它后端，也需要稳定插槽

## 6. 分阶段实施建议

### 阶段 P0：先修正确性和契约

目标：

- 先把已经确认的问题收口，恢复门禁可信度

范围：

- 修复多进程块排序
- 修复 GPU 能力判断对 `torch preload` 的隐式依赖
- 修复批处理包装器测试契约漂移

### 阶段 P1：建立复杂场景基线

目标：

- 让后续优化不再靠主观感受判断

范围：

- 建立复杂图片与复杂视频样本集
- 统一记录 FPS、显存峰值、首帧时延、残留水印率、时序闪烁分数
- 补齐 1080p / 4K 压力回归

### 阶段 P2：复杂图片优化

目标：

- 提升静态复杂背景下的掩码精度与修复质量

范围：

- 强化分割优先路径
- 抽出 `MaskRefiner`
- 新增面向透明边、斜边、镂空结构的细化策略
- 建立“小区域优先 OpenCV / 大区域优先 LaMa”的更稳定路由

### 阶段 P3：复杂视频优化

目标：

- 先解决时序一致性，再追求更高吞吐

范围：

- 引入 `TemporalCoordinator`
- 增加关键帧检测与中间帧掩码传播
- 增加失配重检
- 在修复区域上做时序去闪烁

### 阶段 P4：实验性高质量视频模式

目标：

- 为极复杂视频提供更高质量但更重的路径

范围：

- 新增实验性视频级修复后端抽象
- 保持与当前 `trace / manifest / fallback` 契约一致
- 不进入默认主链

## 7. 测试与指标

### 7.1 必须建立的核心指标

- FPS
- 显存峰值
- 首帧时延
- 残留水印率
- 时序闪烁分数
- 回退触发率

### 7.2 最小困难样本集

- 复杂图片 20 张
  - 半透明角标
  - 镂空文字
  - 彩色渐变 Logo
  - 低码率压缩图
  - 强纹理背景
- 复杂视频 10 段
  - 移动角标
  - 缩放 / 旋转水印
  - 运动模糊
  - 低码率长视频
  - 4K 高纹理背景

---

## 8. 风险与回退策略

### 8.1 主要风险

- 引入更多时序状态后，取消/恢复/异常路径会更复杂
- 更强的 mask 细化如果没有指标约束，可能提升召回却放大过修
- 视频级高质量模式一旦直接暴露为默认选项，容易把显存压力与失败率一起抬高

### 8.2 回退原则

- 默认模式必须继续保持当前稳定路径可用
- 所有新增增强都应具备可关闭开关
- 实验性高质量模式必须显式标注，不进入默认链路

---

## 9. 最终建议

本项目下一阶段最值得做的，不是继续堆更多阈值和形态学参数，而是：

1. 先修掉已确认的正确性问题和契约问题
2. 把复杂图片的核心问题收敛为“更好的 mask”
3. 把复杂视频的核心问题收敛为“更稳定的时序传播与去闪烁”
4. 最后再为高质量视频模式接入更重的时序修复后端

这条路线能最大化复用当前工程成果，同时把后续复杂能力的扩展风险控制在可接受范围内。
